3. 推荐方案：GitHub Actions

为什么选 GitHub Actions？

  • 仓库已在 GitHub（git@github.com:BH6340/ICube.git），零迁移成本
  • 免费额度充足：公开仓库无限分钟，私有仓库 2000 分钟/月
  • Secrets 管理内置：SSH key、服务器地址等可直接配置为 GitHub Secrets
  • 与已有部署脚本无缝衔接：CI 跑测试，CD 通过 SSH 调用 deploy_update.sh
  • 无需额外基础设施：不需要自建 Jenkins/GitLab Runner

4. CI 持续集成设计

触发条件

  • Pull Request 到 main 分支：运行全部检查
  • Push 到 main 分支：运行检查 + 触发 CD

Job 1：后端检查

# .github/workflows/ci.yml（后端 Job 示意）
backend-check:
  runs-on: ubuntu-latest
  services:
    # 测试模式已内置 SQLite 内存库 + Mock Redis，无需外部服务
  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-python@v5
      with:
        python-version: '3.13'
    - name: 安装依赖
      working-directory: cube_api
      run: |
        pip install -r requirements.txt
    - name: Lint（ruff）
      run: pip install ruff && ruff check cube_api/
    - name: 类型检查（mypy）
      run: |
        cd cube_api
        mypy cube_api/apps/ --ignore-missing-imports
    - name: 运行测试
      working-directory: cube_api
      run: python manage.py test --settings=cube_api.settings.dev

关键优势：项目已有 if 'test' in sys.argv 自动切换 SQLite 内存库 + Mock Redis + 禁用限流 + MD5 哈希，CI 环境无需 MySQL/Redis 服务。

Job 2：前端构建验证

frontend-check:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-node@v4
      with:
        node-version: '20'
        cache: 'npm'
        cache-dependency-path: cube_front/package-lock.json
    - name: 安装依赖
      working-directory: cube_front
      run: npm ci
    - name: 构建验证
      working-directory: cube_front
      run: npm run build

说明：前端目前无测试框架（package.json 只有 dev/build/preview），构建验证是最低成本的 CI 检查。后续可选添加 ESLint 和 Vitest。

Job 3：Docker 构建验证

docker-build:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - name: 构建后端镜像
      run: docker build -t icube-api-test ./cube_api
    - name: 构建前端镜像
      run: docker build -t icube-front-test ./cube_front
    - name: 验证 compose 配置
      run: docker compose config -q

价值：确保 Dockerfile 和 compose 配置始终可用，避免部署时才发现构建失败。

5. CD 持续部署设计

部署流程

  1. 触发：push 到 main 且 CI 全部通过
  2. SSH 连接服务器（使用 GitHub Secrets 中的 SSH 私钥）
  3. 数据备份：执行 backup.sh（migrate 前的安全网）
  4. 执行部署：./scripts/deploy_update.sh（已有智能更新逻辑）
  5. 健康检查：HTTP 请求验证服务可用性
  6. 失败通知：GitHub Actions 发送邮件通知

CD Workflow 示意

# .github/workflows/deploy.yml
deploy:
  needs: [backend-check, frontend-check, docker-build]
  if: github.ref == 'refs/heads/main' && github.event_name == 'push'
  runs-on: ubuntu-latest
  steps:
    - name: SSH 部署到服务器
      uses: appleboy/ssh-action@v1
      with:
        host: ${{ secrets.SERVER_HOST }}
        username: ${{ secrets.SERVER_USER }}
        key: ${{ secrets.SSH_PRIVATE_KEY }}
        script: |
          cd /home/bh/ICube
          # 数据库备份
          ./scripts/backup.sh
          # 执行智能更新
          ./scripts/deploy_update.sh --mode full
          # 健康检查
          curl -sf https://icube.com/api/home/banners/ || exit 1

回滚策略

方案 A（推荐，零成本）：Git 回滚 + 重新部署

# 服务器上执行
cd /home/bh/ICube
git log --oneline -5                    # 找到上一个稳定版本
git revert HEAD                         # 或 git reset --hard 
./scripts/deploy_update.sh --mode full  # 重新部署

方案 B（进阶，可选）：Docker 镜像标签版本化

  • 每次部署构建镜像时打两个标签：latest 和 git-sha
  • 回滚时修改 docker-compose.yml 的 image tag 到上一个 sha
  • 需要额外搭建镜像仓库（Docker Hub 免费版或自建 Harbor）

Secret 名称用途示例

SERVER_USERSSH 用户名bh
SSH_PRIVATE_KEYSSH 私钥（用于免密登录）-----BEGIN OPENSSH PRIVATE KEY-----...

安全注意事项：

  • SSH 私钥仅用于部署，不要赋予 sudo 权限
  • 服务器上的 .env 文件（含 DB 密码、SECRET_KEY、支付宝密钥）不经过 CI，始终在服务器本地管理
  • 支付宝密钥 apps/shop/keys/ 已在 .gitignore 中排除，不会进入 CI
  • SSL 证书 nginx/ssl/*.pem 同样已排除

7. 风险与注意事项

风险项严重度应对方案
数据库 migrate 失败 高
  • 部署前自动执行 backup.sh 数据库备份
  • migrate 失败时 SSH action 自动失败，GitHub 发邮件告警
  • 服务器上可手动 git reset + 恢复备份
部署期间服务短暂不可用 中
  • docker compose up -d --build 会先构建再替换，停机约 10-30 秒
  • 可接受（个人项目），如需零停机需引入蓝绿部署（复杂度高，暂不推荐）
  • 建议在低峰期触发部署
SSH 密钥泄露 高
  • GitHub Secrets 加密存储，不会在日志中明文输出
  • 建议使用独立部署密钥，不与开发密钥混用
  • 定期轮换密钥
前端无测试覆盖 中
  • CI 只做 npm run build 验证，无法拦截运行时错误
  • 建议后续添加 ESLint（静态检查）和 Vitest（单元测试）
  • 作为渐进式改进，不阻塞 CI/CD 上线
构建时间过长 中
  • Docker 多阶段构建 + npm/pip 缓存
  • GitHub Actions 缓存 node_modules 和 ~/.cache/pip
  • 三个 Job 并行执行，总时间约 3-5 分钟
服务器资源不足 中
  • 构建在 GitHub Actions Runner 上执行，不占用服务器资源
  • 服务器只需 git pull + docker compose up，资源消耗低
移动端 APK 构建 低
  • cube_app 的 APK 构建依赖 Android SDK，CI 环境配置复杂
  • 建议首期不纳入 CI/CD，保持手动 build-apk.ps1 构建
  • 后续可单独建一个 APK 构建流水线

  • 前端：npm ci → npm run build

  • 验收标准：PR 自动触发检查，红色/绿色状态可见
2

Phase 2：CD 自动部署（预计 1-2 小时）

  • 配置 GitHub Secrets（SERVER_HOST、SSH_PRIVATE_KEY 等）

  • SSH action 调用已有 deploy_update.sh

  • 部署失败邮件通知（GitHub 内置）

  • 移动端 APK CI 构建（需要 Android SDK 的 GitHub Actions 镜像）
  • 分支策略引入 develop 分支 + 预发布环境

9. 结论

可行性评估：高度可行，推荐立即实施 Phase 1-2。

理由：

  • 基础设施就绪度高：Docker Compose 编排完整、Dockerfile 多阶段构建、部署脚本已有智能更新逻辑，CI/CD 只需"串联"现有能力
  • 后端测试已覆盖：6 个 App + utils 都有测试目录，且测试模式自动隔离（SQLite + Mock Redis），CI 环境零额外配置
  • GitHub Actions 零成本：仓库已在 GitHub，私有仓库 2000 分钟/月足够（每次 CI 约 5-8 分钟）
  • CD 复用已有脚本：deploy_update.sh 已有智能变更检测（前端/后端/migration/compose），无需重写部署逻辑

主要前提条件：

  • 服务器需配置 SSH 密钥认证（deploy_02_app.sh 已处理）
  • GitHub Secrets 配置 3-4 个变量
  • 确认 deploy_update.sh 在服务器上的路径和权限

预计总工时：4-6 小时（Phase 1-3），Phase 4 按需投入。
