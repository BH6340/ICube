## 1. 本地开发

### 1.1 一键启动/停止/重启（推荐）

使用 `scripts/dev-local.ps1` 同时管理后端（8000）、Web 前端（5173）、移动端（5174）三个服务。

```powershell
# 启动全部服务
.\scripts\dev-local.ps1 start

# 停止全部服务
.\scripts\dev-local.ps1 stop

# 重启全部服务
.\scripts\dev-local.ps1 restart
```

- 自动从项目根目录 `.env` 读取环境变量注入子进程
- 日志输出到 `.dev-local/` 目录（`backend.out.log` / `frontend.out.log` / `app.out.log`）
- 通过 PID + 启动时间双重校验，避免误杀复用 PID 的进程

### 1.2 单独启动后端

```powershell
cd cube_api
E:\software\python\python313\env\cube_api\Scripts\python.exe manage.py runserver 8000 --settings=cube_api.settings.dev
```

### 1.3 单独启动前端

```powershell
# Web 前端
cd cube_front
npm run dev

# 移动端
cd cube_app
npm run dev
```

### 1.4 前端构建

```powershell
cd cube_front
npm run build
```

构建产物在 `cube_front/dist/`，生产环境由 Dockerfile 自动构建，无需手动操作。

### 1.5 自动拉取代码

每天定时拉取远程仓库最新代码，保持本地同步。

```powershell
# 手动执行一次
.\scripts\auto-pull.ps1
```

- 工作区有未提交改动时跳过，不破坏本地修改
- 使用 `git pull --rebase` 保持线性历史
- 日志输出到 `.dev-local/auto-pull.log`

### 1.6 注册自动拉取计划任务

注册 Windows 计划任务，每天 08:00 自动执行 `auto-pull.ps1`。

```powershell
# 需以管理员权限运行
.\scripts\register-autopull.ps1
```

- 任务名：`ICube-AutoPull`
- 每天 08:00 触发，错过启动时间会补跑
- 支持 pwsh 和 powershell 自动适配

### 1.7 Markdown 转 PDF

将 Markdown 文件转换为带目录、支持 Mermaid 图表的 PDF，输出到 md 文件所在目录。

```powershell
# 交互模式（逐步确认）
python scripts/md2pdf_converter.py

# 转单个文件
python scripts/md2pdf_converter.py README.md

# 转指定目录（不递归）
python scripts/md2pdf_converter.py docs/guides

# 递归子目录 + 跳过确认
python scripts/md2pdf_converter.py docs/wiki -r -y

# 绝对路径
python scripts/md2pdf_converter.py E:\BH\PyStudy\ICube\docs\guides\测试文档.md
```

常用选项：

| 选项 | 说明 |
|------|------|
| `-r`, `--recursive` | 递归子目录（默认不递归） |
| `-y`, `--yes` | 跳过所有确认，直接执行 |
| `--page-size A4` | 页面大小，默认 A4 |
| `--no-toc` | 不生成目录 |
| `--no-mermaid` | 禁用 Mermaid 图表 |
| `--no-overwrite` | 不覆盖已存在的 PDF（自动重命名） |

依赖安装：

```bash
pip install md2pdf-mermaid
playwright install chromium
```

### 1.8 手动拉取代码注意事项

**场景 A：日常开发中，本地有未推送的提交，想同步远程最新代码**

推荐 `git pull --rebase origin dev`。这会保留你的本地提交，并接到远程最新提交之后，保持历史线性。

**场景 B：服务器部署时，本地有一些临时调试改动，想直接丢弃并同步远程**

推荐 `git fetch origin && git reset --hard origin/dev`。服务器上的临时改动一般不需要保留，强制同步到远程状态更干净，部署也更可靠。

**场景 C：在 CI 流水线中，需要确保代码与远程完全一致**

推荐 `git fetch origin && git reset --hard origin/dev`。CI 环境需要可复现的构建结果，任何本地残留都可能导致不可预期的行为。

**场景 D：你希望保留服务器上的本地改动，同时拉取远程更新**

推荐先 `git stash` 暂存本地改动，再 `git pull --rebase`，最后 `git stash pop` 恢复改动。这样既保留了本地配置或调试代码，又能同步远程最新提交。



## 2. Docker 容器管理

### 2.1 编译并启动全部服务

```bash
sudo docker compose up -d --build
```

### 2.2 停止并删除（含数据卷）

彻底停止并删除所有容器与旧的数据卷（用于清理死锁的权限表等场景）。

```bash
sudo docker compose down -v
```

> ⚠️ `-v` 会删除数据卷，数据库数据会丢失，谨慎使用。

### 2.3 重启服务

```bash
# 重启后端（代码在镜像内时不生效，需重新构建）
sudo docker compose restart api

# 重启前端 + Nginx
sudo docker compose restart front nginx

# 同时重启多个
sudo docker compose restart api front nginx
```

> API 代码位于镜像内，代码更新后仅 `restart` 不会加载新代码，必须重新构建镜像。

### 2.4 查看状态和日志

```bash
# 查看所有服务状态
docker compose ps

# 实时查看日志
docker compose logs -f api
docker compose logs -f api nginx

# 查看最近 100 行
docker compose logs --tail 100 api
```

### 2.5 创建超级用户

```bash
docker compose exec api python manage.py createsuperuser
```

## 3. 生产部署

使用 `scripts/deploy.sh` 一键部署，支持三种模式。

```bash
# 全量构建、迁移并启动全部服务（默认）
bash scripts/deploy.sh full

# 仅构建 API、执行数据库迁移并重启 Nginx
bash scripts/deploy.sh api

# 仅构建前端并重启 Nginx
bash scripts/deploy.sh front
```

### 注意事项

- **禁止使用 sudo 运行整个脚本**，当前用户需拥有 Docker 权限
- 脚本依次完成：git pull → 构建镜像 → 停止 API → 迁移并备份媒体 → 启动 DB/Redis → 执行 migration → 启动全部服务 → 验证状态
- 首次生产部署或包含重要数据库迁移时，应先单独备份 MySQL
- 适合场景：首次部署、代码推送后发布新版本、Dockerfile/Compose/migration 更新后
- 不适合日常本地开发，每次执行都会拉取代码、构建镜像并重启服务

Windows 下运行需使用 Git Bash 或 WSL：

```bash
cd /e/BH/PyStudy/ICube
bash scripts/deploy.sh full
```

## 6. 数据库备份

所有脚本位于 `scripts/` 目录，自动推算项目根目录，可从任意位置运行。

### 6.1 本地导出（pymysql 直连）

导出本地 MySQL 数据库结构和数据到 `init_data.sql` 并推送到 Git。

```bash
python scripts/update_db_dump.py
```

支持的环境变量（可通过 `.env.backup` 加载）：

| 变量 | 说明 | 默认值 |
|------|------|--------|
| `DB_HOST` / `DB_USER` / `DB_PASSWORD` / `DB_NAME` / `DB_PORT` | 数据库连接 | - |
| `OUTPUT_FILE` | 输出文件名 | `init_data.sql` |
| `MEDIA_DIR` | 媒体目录 | `media` |
| `DRY_RUN` | 设为 `true` 预览不执行 | - |
| `EMAIL_ENABLED` / `EMAIL_USER` / `EMAIL_PASSWORD` / `EMAIL_TO` | 邮件通知 | - |

### 6.2 服务端导出（Docker mysqldump）

通过 `docker compose exec` 在服务端导出 Docker MySQL 数据库到 `init_data.sql` 并推送到 Git。

```bash
python scripts/server_db_dump.py
```

常用参数：

```bash
# 预览不执行
python scripts/server_db_dump.py --dry-run

# 只导出不推送
python scripts/server_db_dump.py --no-push

# 不提交媒体文件
python scripts/server_db_dump.py --no-media
```

推送逻辑：push 前先执行 `git pull --rebase` 同步远端；推送失败自动重试，最多 3 次，间隔 30 秒，每次重试前再次 pull 同步。若 rebase 冲突会自动 `rebase --abort` 保留本地提交。

### 6.3 一键备份脚本（Shell 包装，适合 cron）

```bash
# 本地备份（调用 update_db_dump.py）
bash scripts/backup.sh

# 服务端备份（调用 server_db_dump.py）
bash scripts/server_backup.sh
```

### 6.4 cron 定时任务示例

```bash
# 每天 22:00 执行服务端备份
0 22 * * * /home/bh/ICube/scripts/server_backup.sh >> /home/bh/ICube/logs/server-backup-cron.log 2>&1
```

逐段拆解：

| 部分 | 含义 |
|------|------|
| `0 22 * * *` | cron 时间表达式：每天 22:00 执行 |
| `/home/bh/ICube/scripts/server_backup.sh` | 要执行的脚本（绝对路径） |
| `>>` | 追加输出到文件（不覆盖） |
| `2>&1` | 标准错误重定向到标准输出，错误信息也写入同一个日志文件 |

整体含义：每天晚上 10 点自动执行 `server_backup.sh`，脚本导出数据库到 `init_data.sql` 并推送到 Git，所有输出（含错误）追加写入 `server-backup-cron.log`。

## 7. APK 构建

使用 `scripts/build-apk.ps1` 一键构建 Android APK 并可选上传到服务器。从 `cube_app/package.json` 读取版本号，生成带版本号的文件名（如 `icube-v1.0.0.apk`）。

```powershell
.\scripts\build-apk.ps1
```

### 4 步流程

1. **构建前端资源** — Vue + Vite 产物 → `cube_app/dist/`
2. **同步 Capacitor** — `dist/` 复制到 `android/app/src/main/assets/public/`
3. **构建 APK** — Gradle `assembleDebug`，JDK 路径由 `gradle.properties` 指定
4. **重命名并上传** — 复制为 `icube-v<version>.apk`，同时复制到本地 `downloads/`，scp 到服务器 `downloads/` 目录

### 前置条件

- 已安装 Node.js、Android SDK、JDK 21
- 可选：设置环境变量 `SCP_USER` 和 `SCP_HOST` 自动上传，否则交互式询问

### 输出

- 本地路径：`cube_app/android/app/build/outputs/apk/debug/icube-v<version>.apk`
- 下载地址：`http://<服务器IP>/apk/icube-v<version>.apk`
