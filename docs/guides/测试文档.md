## 1. 测试概述

本项目是一个魔方学习网站（ICube）的后端系统，基于 Django 6.0 + Django REST Framework 构建。测试覆盖以下核心业务模块：

| 模块 | 功能描述 | 测试重点 |
|------|----------|----------|
| **accounts** | 用户认证、资料管理、关注系统 | JWT 认证、用户 CRUD、关注/取消关注、日志脱敏 |
| **formula** | 魔方公式库、分类、状态、匹配 | 公式逆运算、状态验证、公式匹配、收藏与公开收藏 |
| **shop** | 商城系统：商品、购物车、订单、地址 | 订单状态流转、库存并发控制、用户隔离 |
| **forum** | 社区论坛：帖子、评论、点赞、收藏 | 帖子 CRUD、评论层级、互动功能、热门排序 |
| **timer** | 计时器：记录、统计 | 计时记录 CRUD、魔方类型与方法 |
| **home** | 首页数据聚合 | 轮播图、公告、首页接口 |
| **utils** | 工具函数：图片处理、URL 生成 | 图片压缩、格式转换、URL 构建 |

## 2. 测试技术栈

| 技术 | 用途 |
|------|------|
| **pytest** | 测试运行器（替代 manage.py test） |
| **pytest-django** | Django 集成支持 |
| **pytest-cov** | 覆盖率报告生成 |
| **Django TestCase** | 基础测试类，提供数据库回滚机制 |
| **APITestCase / APIClient** | REST API 接口测试 |
| **SimpleTestCase** | 不涉及数据库的单元测试（如日志脱敏测试） |
| **unittest.mock** | 外部依赖 Mock（如 Redis 连接失败、支付宝回调） |
| **SQLite 内存数据库** | 测试环境自动切换，加速测试 |
| **Loguru sink** | 捕获日志输出，验证敏感信息脱敏 |

## 5. 测试方法

### 5.1 测试环境配置

测试环境通过 `settings/dev.py` 中的 `_IS_TEST = 'test' in sys.argv or 'pytest' in sys.modules` 自动检测，兼容 `manage.py test` 和 `pytest` 两种运行方式：

| 配置项 | 测试环境值 | 说明 |
|--------|-----------|------|
| **数据库** | SQLite 内存数据库（`:memory:`） | 无需 MySQL，随进程销毁 |
| **缓存** | LocMemCache（内存缓存） | 无需真实 Redis，纯 Python 内存实现 |
| **Redis 直连** | fakeredis.FakeRedis() | 模拟 Redis 原生命令（exists/sadd/scard 等） |
| **密码哈希** | MD5PasswordHasher | 不可用于生产，仅为加速测试 |
| **限流** | 超大速率（1000/min） | 不禁用但设超大值，避免触发限流 |
| **分页** | DRF 默认 PageNumberPagination | 统一分页结构 |
| **Redis 连接** | `mock_get_redis_connection` | 返回 fakeredis 客户端，兼容 Redis 原生命令 |

#### 双 Redis 模拟机制（重要）

项目代码有两种 Redis 访问方式，测试环境分别替换为不同的模拟实现：

| 代码访问方式 | 生产环境 | 测试环境 | 用途举例 |
|-------------|---------|---------|---------|
| `from django.core.cache import cache` → `cache.set/get/delete` | `django_redis.cache.RedisCache` | **LocMemCache** | 帖子缓存、页面缓存、API 缓存 |
| `from django_redis import get_redis_connection` → `con.exists/sadd/scard` | 真实 Redis | **fakeredis.FakeRedis()** | JWT 黑名单、关注/粉丝集合、限流计数 |

**为什么需要两个？**

LocMemCache 只实现了 Django cache 的标准 API（`set/get/delete/incr`），没有 Redis 特有的集合操作（`sadd/scard/smembers/sismember`）。项目代码中 `accounts/services.py` 等使用了 Redis 原生命令来操作关注/粉丝集合和 JWT 黑名单，因此需要 fakeredis 来模拟这些命令。

**切换实现（`settings/dev.py`）：**

```python
# _IS_TEST = 'test' in sys.argv or 'pytest' in sys.modules

# 方式1：Django cache framework → LocMemCache
if _IS_TEST:
    CACHES = {
        'default': {
            'BACKEND': 'django.core.cache.backends.locmem.LocMemCache',
            'LOCATION': 'icube_test_cache',
            'KEY_PREFIX': 'icube_test',
            'TIMEOUT': 300,
        }
    }

# 方式2：原生 redis-py 客户端 → fakeredis
if _IS_TEST:
    import django_redis
    import fakeredis
    _fake_redis = fakeredis.FakeRedis()
    def mock_get_redis_connection(alias):
        return _fake_redis
    django_redis.get_redis_connection = mock_get_redis_connection
```

**各负责什么场景：**

| 场景 | 使用的模拟器 | 代码示例 |
|------|------------|---------|
| 帖子缓存、轮播图缓存 | LocMemCache | `cache.set('post:1', data)` |
| `@cache_page` 装饰器 | LocMemCache | API 响应缓存 |
| JWT 黑名单检查 | fakeredis | `con.exists('jwt:blacklist:xxx')` |
| 用户关注集合 | fakeredis | `con.sadd('user:1:following', 2, 3)` |
| 关注数量统计 | fakeredis | `con.scard('user:1:following')` |
| 获取粉丝列表 | fakeredis | `con.smembers('user:1:followers')` |

**测试中注意事项：**

1. fakeredis 是全局单例（`_fake_redis`），测试间数据不自动清理
2. 如果测试写了 Redis 数据，`setUp` 中需 `con.flushall()` 或删指定 key
3. LocMemCache 天然隔离，每个 `TestCase` 的 cache 在 `tearDown` 后自动清理
4. 不要直接 `import fakeredis`，通过 `get_redis_connection()` 拿连接
5. 两者配合使本地与 CI 行为完全一致，无需真实 Redis 服务

### 10.3 缓存与 Redis 问题

**Q: 测试之间缓存未清理导致失败？**
```python
# 每个基类的 setUp 和 tearDown 已自动调用 cache.clear()
# 如需手动清理：
from django.core.cache import cache

def setUp(self):
    cache.clear()
    ...

def tearDown(self):
    cache.clear()
    ...
```

**Q: 测试环境使用哪个 Redis 数据库？**

测试环境无需真实 Redis 服务。`CACHES` 使用 `LocMemCache`（Django 内置内存缓存），`get_redis_connection` 返回 `fakeredis.FakeRedis()` 实例。两者配合覆盖所有缓存和 Redis 直连场景，本地与 CI 行为完全一致。如需手动清理：

```python
from django.core.cache import cache

def setUp(self):
    cache.clear()
    ...
```

## 11. CI/CD 自动化测试

### 11.1 GitHub Actions 工作流

项目通过 `.github/workflows/cicd.yml` 配置了 CI/CD 流水线，在 push/PR 到 `main` 分支时自动触发。

### 11.2 Job 触发规则（Path Filter）

| 文件变更 | 触发的 Job | 跳过的 Job |
|---------|-----------|-----------|
| `cube_api/**` | 后端 Lint + Test | 前端、Docker |
| `cube_front/**` | 前端 Build 验证 | 后端、Docker |
| `docker-compose.yml` / `Dockerfile` | Docker 构建验证 | 后端、前端 |
| `scripts/**` | 仅部署 | 后端、前端、Docker |
| `docs/**` / `*.md` | **不触发任何 Job** | 全部跳过 |

### 11.3 CI Job 说明

| Job | 内容 | 预计耗时 |
|-----|------|---------|
| **后端 Lint + Test** | ruff 代码检查 + pytest 全量测试 + 覆盖率报告 | ~2min |
| **前端 Build 验证** | npm ci + vite build | ~2min |
| **Docker 构建验证** | 前后端 Dockerfile 构建 + compose config 校验 | ~3min |

CI 产物：
- **覆盖率报告**：`coverage-report` artifact（保留 30 天），含 XML 格式覆盖率数据
- **部署日志**：`deploy-log-{run_id}` artifact（保留 90 天），含部署完整 stdout

### 11.4 CD 自动部署

- **触发条件**：push 到 `main` + CI Job 全部通过（或被跳过）
- **部署流程**：SSH → backup.sh → deploy_update.sh --non-interactive → HTTP 健康检查
- **健康检查**：前端 `http://localhost/` + API `http://localhost/api/home/banners/`
- **失败处理**：健康检查失败时输出容器日志并退出
- **部署日志持久化**：部署 stdout 保存为 GitHub artifact（保留 90 天），在 Actions run 页面可直接下载查看
- **自动 CHANGELOG**：部署成功后自动从 git log 生成 `CHANGELOG.md`，按 conventional commit 类型分组（feat/fix/docs/refactor 等），提交回 main 分支
- **微信通知**：部署成功/失败均通过 Server酱推送微信通知，含 commit 信息、时间和 Actions 链接

### 11.5 本地与 CI 一致性

| 维度 | 本地 | GitHub CI |
|------|------|-----------|
| 数据库 | SQLite 内存库 | SQLite 内存库 |
| 缓存 | LocMemCache | LocMemCache |
| Redis | fakeredis | fakeredis |
